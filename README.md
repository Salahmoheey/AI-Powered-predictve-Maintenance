# HexaMind – NASA C-MAPSS FD001

HexaMind is a machine predictive-maintenance project using the NASA C-MAPSS FD001 turbofan engine dataset. The repository contains data preprocessing, rolling feature engineering, engine-level validation utilities, RUL prediction models with uncertainty quantification, and a raw-data replay client for the backend API.

## Run the pipeline

Run commands from the repository root:

```bash
python src/download.py
python src/preprocessing.py
python src/features.py
python src/export_golden_example.py   # only if the pipeline changed
python src/train.py                   # trains XGBoost, LSTM, GRU, and 1D-CNN
pytest -q
```

Preprocessing validates the required schema, numeric and finite values, positive integer engine/cycle IDs, non-negative sensor readings, duplicate engine-cycle pairs, and strictly increasing cycle order. The supplied dataset specification does not define upper physical bounds for every channel, so no unsupported per-sensor upper limits are invented. It calculates constant columns from the training partition only, applies the same dropped-column list to validation and test, and fits `MinMaxScaler` on training rows only. The scaler, the dropped-column list and the model input order are saved under `artifacts/` (committed); reproducible train/validation/test engine IDs and the five GroupKFold folds are saved under `data/splits/` and should be shared/committed. Generated processed/features data are intentionally excluded from Git.

## Model Training & Evaluation

`src/train.py` (backed by `src/models/rul.py`) trains and evaluates four Remaining Useful Life (RUL) architectures on 30-cycle windows of 62 scaled features (piecewise-linear RUL capped at `125`), producing both point predictions and 90% prediction intervals (`pi90`):

- **XGBoost (`xgboost_rul.json`):** Gradient-boosted trees trained with squared-error point regression and quantile regression (`alpha = 0.05` and `0.95` for the 90% prediction interval) alongside 5-fold `GroupKFold` cross-validation.
- **LSTM, GRU, 1D-CNN (`lstm_rul.pt`, `gru_rul.pt`, `cnn1d_rul.pt`):** PyTorch sequence models trained with Mean Squared Error (`MSELoss`) loss, early stopping on validation RMSE, and Monte Carlo Dropout (`mc_samples = 30`) for 90% uncertainty intervals.

Run training for all models or a specific subset:

```bash
python src/train.py                               # train all 4 models (default: 35 epochs, seed 42)
python src/train.py --models gru lstm --epochs 40 # train selected models
```

## Replay raw data to the backend

Copy `data/machine_mapping.example.json` to `data/machine_mapping.json` and replace the sample values with the real
backend machine IDs. Do not assume NASA `unit_id` equals backend `machine_id`.

```bash
export HEXAMIND_API_URL=http://localhost:8000/api/v1   # Windows PowerShell: $env:HEXAMIND_API_URL = "..."
export HEXAMIND_API_TOKEN=<jwt>                       # optional Bearer token
python src/replay.py --dry-run --units 1 --limit 3    # print a request body, no backend needed
python src/replay.py --units 1 --limit 5 --delay 0.2  # smoke test
python src/replay.py                                  # all 100 test engines
```

The replay posts **one request per engine cycle** to `POST /machines/{machine_id}/sensor-logs` with the Stage 4 body
`{"readings": [{"sensor_type", "value", "timestamp"}, ...]}` (24 raw, unscaled channels sharing one timestamp per cycle).
The API owns validation, scaling and feature generation. Full rules: `docs/API_INPUT_CONTRACT.md`;
real-backend test procedure: `docs/REPLAY_INTEGRATION_CHECKLIST.md`.

## Feature windows and validation

`src/features.py` uses a 30-cycle window. Every engineered feature (rolling mean, rolling std, EWMA) depends only on the
last 30 cycles of the same engine, so offline training features and online serving features are identical:
- **Tabular inference (`XGBoost`):** requires the latest **30** raw cycles (`raw_window_to_features`) to produce one 62-feature vector.
- **Sequence inference (`GRU`, `LSTM`, `1D-CNN`):** requires the latest **59** raw cycles (`raw_window_to_sequence`) so that each of the 30 consecutive sequence steps is computed from its full 30-cycle rolling history, yielding an exact `(30, 62)` matrix matching offline training.

`create_windows()` builds fixed-length sequences for deep models. `src/validation.py` provides `GroupKFold(5)` splits grouped by `unit_id` to prevent engine leakage.

## Expected output of the pipeline (FD001)

| Dataset | Rows | Engines | Columns (processed) | Columns (features) |
|---|---|---|---|---|
| Train | 16,561 | 80 | 20 | 65 |
| Validation | 4,070 | 20 | 20 | 65 |
| Test | 13,096 | 100 | 20 | 65 |

Dropped from the 26 raw columns (computed on training rows only): `sensor_1`, `sensor_5`, `sensor_10`, `sensor_16`, `sensor_18`, `sensor_19`, and `setting_3`. The remaining 15 sensors each get three features (rolling mean, rolling std, EWMA), i.e. 15 x 3 = 45 feature columns on top of the 20 processed columns (20 + 45 = 65).

## Assumptions and environment

- **Non-negative sensors:** `validate_data()` rejects any negative sensor reading. This is an FD001-specific assumption; change it if another dataset is used.
- **Scaler compatibility:** `scaler.joblib` is saved with scikit-learn `1.9.1` (see `requirements.txt`). Train, save, and serve with this same version, otherwise loading the scaler may warn or behave differently.
- **Test values outside [0, 1]:** the scaler is fitted on training rows only, so a few test readings fall slightly outside [0, 1]. They are not clipped; decide per model whether clipping is needed.
